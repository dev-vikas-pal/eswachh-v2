The ten things that will catch you out

 

Every one of these has already cost real time here. Each links to the section that explains it.

If this happens…It is almost certainly
A front-end change has no effect at allThe browser is running an old build. npm run dev is stopped, so the page falls back to public/build. Check whether the page references :5173 or /build/assets. (08.6)
A page returns 404 for no reasonThe sector scope. Nothing is signed in, so it covers nothing and returns nothing. Resolve inside SectorContext::withoutScope(). (13)
A price is wrong by a small amountThe quote was built without society_id, so the society surcharge is missing. (13)
A form opens completely blankwatch() with no immediate, on a query whose data was already cached. (13)
A screen does not refresh after savingOnly its own cache was cleared. Use refreshAfter(), never a bare invalidateQueries. (08.8)
The test suite behaves strangelyA cached config is overriding phpunit.xml. Run php artisan config:clear. The suite now refuses to start in that state.
No messages are going outDelivery needs production and WHATSAPP_ENABLED. Outside that, messages are recorded, not sent — which is deliberate. (07)
A message is rejected by the providerThe template name does not exist at MSG91, or its variables were not sent. (08.7)
A setting appears to do nothingCheck something actually reads it. Two on that screen were decorative until recently.
A shell edit corrupts a PHP filesed, awk and perl strip \ from namespaces and mangle UTF-8. Use an editor for PHP and for these guides.

The four rules that are not negotiable

  1. No amount ever comes from a request. Prices are worked out by PriceBook, on the server, at the moment of charging.
  2. Nothing is marked paid except a verified callback.
  3. Scoping fails closed. Covering no sectors returns no rows, never every row.
  4. Don't commit. The owner commits by hand.

The three commands you will use most

php artisan test                # 435 tests, about 70 seconds
npx vue-tsc --noEmit            # the front end; use this, not npm run build
php artisan eswachh:deploy      # migrate, seed, rebuild caches, on any server

Section 01

Getting it running

1.1
# everything: composer, .env, key, migrate, npm, build
composer setup

# the price list, message templates, policies, a first admin
php artisan db:seed

# server + queue + log tail + vite, all four at once
composer dev

composer dev runs php artisan serve, the queue listener, pail and npm run dev together and kills all four when any one stops. Use it rather than four terminals.

What must be in .env

KeyWhy
APP_TIMEZONE=Asia/KolkataNot optional. v1 ran on it. On UTC, imported timestamps are mislabelled by five and a half hours and date filters silently find nothing.
DB_CONNECTION=mysqlThe importer reads a v1 MySQL database directly.
SESSION_DRIVER=databaseSanctum SPA cookie auth.
QUEUE_CONNECTION=databaseMessaging is queued.
One command to answer "is it wired up?"

php artisan eswachh:check-integrations reports whether payments and messaging are configured and, when they are not, exactly what is stopping them. Add --ping to prove the gateway key actually works.

Importing v1 data

app/Console/Commands/ImportLegacyData.php

php artisan eswachh:import brings across customers, vehicles, subscriptions and payments, links every customer to a login that still accepts their old password, and issues invoice numbers for payments that had none. Five v1 orders cannot come across: their customers were deleted in v1, so there is nobody to attach them to.

Onto an empty database it is three commands, and the order is the whole of it:

php artisan migrate         # the tables
php artisan db:seed         # an administrator, the site's words, the message wording
php artisan eswachh:import  # everything else, out of v1

Seeding before importing is right: the seeder creates no masters and no customers, only what a database needs before anybody can sign in.

Three ways this goes wrong, all now checked up front

The database was never migrated. The first thing the command does with any record is ask the legacy map whether it has been seen before, so the error named legacy_references — as though that one table had failed to migrate, when in fact none of them existed. It now says so plainly and prints the three commands.

LEGACY_DB_DATABASE pointed at a v2 database. An old working copy, a backup, or the database the command last imported *into* — all of them connect perfectly well, and several have a states table of their own, so the import gets some way in before anything looks wrong. It now checks for orders, carcategories and payment_history first: v1 kept subscriptions in orders, and v2 has no such table.

v1 is not one schema. payment_id, razorpay_order_id, verified_by and verified_at were added to payment_history part way through its life. Reading one directly on an older backup was a fatal error seven steps in, with the customers, cars and plans already written — the worst place to stop. Optional columns go through column() and a missing one means blank, which is what it meant in v1.

--dry-run reports without writing, --step= runs one stage, and --fresh wipes what was imported and starts again. Note that a dry run reports every payment as "no matching subscription": nothing is written, so nothing is in the map for the payments step to find. That is the dry run being honest, not a problem with the data.

Section 02

How the code is arranged

2.1

Everything is filed by who it is for, not by what kind of file it is. The same four names appear on both sides of the wire.

AudienceBackendFront end
The officeapp/Http/Controllers/Api/V1/Adminresources/js/admin
A customer.../Api/V1/Portalresources/js/portal
A visitor.../Api/V1/Siteresources/js/site
More than one.../Api/V1/Sharedresources/js/shared

Why not group by resource

A SubscriptionController holding everything anyone can do to a subscription hides the only question that matters here: who is asking. A customer holds view.subscription so they can look at their own plan. An ability cannot say "their own"; only a query can. Filing by audience puts that question in the folder name.

Shared is the load-bearing one

Those controllers are reached by both the office and a customer, so each carries a row-level check inside it (RestrictsToOwnRecords). If one is ever moved into Admin, that check starts to look redundant to whoever edits it next — which is exactly how a customer ends up reading the whole branch's payments.

2.2

What is not in that table

FolderHolds
app/Domain/*The business itself: pricing, billing, messaging, the daily round, cloth ledger, complaints, alerts, phone codes. No HTTP, no request objects. A controller validates and delegates; the rules read the same whether a person, a scheduled job or a test called them.
app/Support/*Plumbing that is not a business rule: Tenancy, Access, Http (sorting whitelists, ownership), Settings, Numbering, Content (sanitising), Masters, Legacy, Database, Preferences.
app/ModelsOne flat folder on purpose. Models are referenced from everywhere, and a Subscription filed under Admin would be a lie.

Adding a route

  1. Decide who it is for. That is the folder.
  2. If the answer is "both the office and a customer", it is Shared, and it needs an ownership check — restrictToOwnRecords() for a list, ownsRecord() for a single row, returning 404 and not 403, because refusing must not confirm that the record exists.
  3. Abilities go on the route or at the top of the method. They answer may this person use this feature, never whose rows are these.
routes/api.php — everything behind auth
routes/api_public.php — quotes, signup, renewal lookup, catalogue, blog
routes/web.php — which blade shell serves which URL
routes/console.php — the schedule
Section 03

Sector scoping

3.1
app/Support/Tenancy/SectorContext.php · app/Models/Concerns/ScopedToSectors.php

A sector is the territory, and it is the whole of tenancy. Staff are assigned sectors through user_sector; a customer sits in one sector; a record is visible when those two meet.

users —< user_sector >— sectors —< customers —< subscriptions —< service_logs
                                     ∴ vehicles, complaints, cloth_entries

One rule: a customer is visible to whoever covers the sector the customer sits in. Nothing is copied onto the customer, so reassigning a sector is one pivot row and takes effect on the next request.

SectorContext::currentSectorIds()     // null for an admin, their ids otherwise
SectorContext::currentCustomerId()    // set only when the viewer IS a customer
SectorContext::isRestricted()         // false only for super_admin
SectorContext::withoutScope(fn () => ...)   // masters, cross-sector checks
SectorContext::forSectors($ids, fn () => ...) // jobs, importers, tests
SectorContext::forget($userId)        // after their assignment changes
SectorContext::reset()                // tests, in setUp and tearDown
currentSectorIds answers null inside withoutScope

Null means "ask nothing of this query", which is right for the scope and wrong everywhere else. Called inside an unscoped block it turned every franchise user's own territory into an empty list on /me. Resolve it before lifting the scope.

What each model declares

Put use ScopedToSectors; on a model and it reduces to "which customers may this viewer see". Three tables do not and say so in sectorScope():

TableScoped by
paymentsA stamped sector_id, written at capture and never recomputed. A payment records something that happened, so who took the money does not change when territory is rearranged — hand a sector over and the new holder gets the customers and the plans, but last year's figures do not change shape.
attendancescleaner_id against the staff covering the viewer's sectors — the same pivot, asked from the other end.
sectorsTheir own id: you see the ones you are assigned.
404, not 403

A record in another sector must produce the same response as one that never existed. A 403 confirms there is something there to be refused, which is itself a leak — it tells a franchise user that a car number belongs to somebody, somewhere.

3.2

Three rules that are easy to get wrong

  • Fail closed. Covering nothing returns nothing, never everything. That is the difference between a quiet screen and a leak.
  • A customer with no sector_id belongs to nobody until one is given. SQL IN never matches null, so the rule needs no special case — but sector_id is therefore required when the office creates a customer, or it silently makes an invisible one.
  • A customer is never in the pivot. Their territory comes from their address; an assignment would let them see their neighbours. The scope asks currentCustomerId() first and narrows to their own records instead.

Assigning territory

On the person, under People — that is the moment it matters, because an account created without a sector signs in to empty screens. The Sectors screen reports who covers each one but does not edit it.

Nobody hands out territory they do not hold: a franchise owner adding a cleaner can only give them sectors from their own, or assigning a colleague elsewhere would be a way to read another franchise's customers through them.

When to use withoutScope

Only for things that are genuinely shared, and always with a comment saying why: masters (every franchise sells from the same price list, and this is why a quote works on the public site with nobody signed in), and uniqueness of a car number, since a car on another sector's books is still taken.

The scope's own subqueries use the query builder rather than Eloquent, deliberately: they run inside the global scope that would otherwise call them again, and they must see soft-deleted rows so withdrawing a society does not hide its customers from the person still servicing them.

What this replaced

A branch_id copied onto the customer and onto everything of theirs. That column was a cache of where somebody lived, and it went stale: a sector was pointed at another franchise and two hundred customers stayed in the old owner's books while the sector claimed otherwise, with nothing anywhere reporting the disagreement. The columns are still on the tables, nullable and unread, until the model has run long enough to be trusted.

Section 04

Roles and abilities

4.1
app/Enums/UserRole.php · app/Support/Access/Abilities.php · app/Models/CustomRole.php

Four roles, declared in code rather than in tables: super_admin, franchise_owner, cleaner, customer. Abilities are named {verb}.{resource} and listed on the enum. super_admin is granted everything by a Gate::before hook, which keeps the table readable.

Why in code

v1 stored roles and permissions in tables and then cached the lookup — a cache that shadowed the relation and left newly created users with no roles at all until somebody cleared it by hand. Abilities declared in code cannot drift out of sync with themselves, cannot be cached wrongly, and are visible in review.

Adding an ability

  1. Add the string to the relevant arm of UserRole::abilities().
  2. Add it to Abilities so the roles screen can offer it.
  3. Check it on the route or at the top of the method.
  4. If it is a screen, add it to the navigation array in resources/js/admin/AppLayout.vue and to the route's meta.ability.
Never name an ability "own"

An ability answers may this person use this feature. Which rows they see is a separate question that only a query can answer. Naming one view.own.complaint implied otherwise and left routes checking view.complaint locking customers out of their own complaints entirely.

Custom roles

DB-backed, and each refines one built-in role: it starts from that role's abilities and may only narrow or pick from within them. A custom role cannot grant cross-branch sight; there is no way to express it. Managing roles is gated on being super_admin, not on an ability, so that a role cannot be used to grant the power to rewrite roles.

Section 05

Money

5.1
app/Domain/Pricing/PriceBook.php · Quote.php · QuoteLine.php
( category + package + service_type + society surcharge ) × months
    − duration discount
    + cloth bundle

Every master is looked up fresh on each call. A quote is a statement about the price list as it stands right now, and must never be assembled from ids the caller has already resolved to amounts. A master that was asked for and cannot be sold produces a warning rather than being skipped — skipping it silently under-prices the plan by whatever it used to charge, and nobody would notice. Withdrawn and never-existed are told apart, because they need different fixes.

Rule one · no amount ever comes from a request

Every price is worked out by PriceBook, on the server, at the moment it is charged. The figure the browser shows is a quote and is thrown away. v1 read final_price straight from the form and validated only min:1 — a customer could have paid ₹1 for any plan.

There is a test for this on every paying route. If you add one, add the test: post a wrong amount_paise and assert the stored amount ignored it.

Rule two · nothing is marked paid except a verified callback

Signup, renewal, top-up and add-a-car all open a payment and stop. Domain\Billing\RecordPayment moves it, and only after the Razorpay signature checks out and the gateway confirms what it holds.

5.2

The billing pieces

ClassDoes
StartPaymentOpens a payment row and a gateway order, before the window appears, so an abandoned checkout still leaves a record.
RecordPaymentThe only thing that marks anything paid. Idempotent.
RazorpaySignatureHMAC verification, constant-time.
RazorpayGatewayThe HTTP client. Reports itself unavailable unless enabled and keyed.
InvoiceNumberIssues a numbered invoice per captured payment, prefix from settings.

Paise, everywhere

All money is an integer number of paise, named *_paise. Never a float, never a decimal column, no exceptions. Format for display at the edge only.

Repricing on renewal

app/Http/Controllers/Api/V1/Shared/RenewalController.php

A customer renewing from their account may change package, service type and duration. The controller reprices and writes the new amount before opening the payment. Without that step a customer switching one month to six would be charged for one.

Section 06

Messaging

6.1
app/Domain/Messaging/Messenger.php · app/Enums/MessagePurpose.php · database/seeders/MessageTemplateSeeder.php

The delivery gate

public function deliveryEnabled(): bool
{
    // Never during tests, whatever the configuration says.
    if (app()->runningUnitTests()) {
        return false;
    }

    return app()->isProduction() && (bool) config('services.whatsapp.enabled');
}
This is the line that matters

A message leaves the building only when the app is in production and WHATSAPP_ENABLED=true. Everywhere else it is written to the messages table exactly as it would have been sent, together with a suppressionReason() saying why it was held. Demonstrations against real data cannot message a real customer.

Do not add a bypass for "just this one". If you need to see delivery work, point a staging copy at a test number.

Wording lives in the database

Templates are seeded with the exact wording from the requirements document and edited in the office. A template that is missing or switched off sends nothing, rather than falling back to wording nobody has approved. Both the nightly jobs and hand-sent messages read the same row.

The dedupe key

MessagePurpose values are load-bearing: the purpose is half of the key that stops a customer being messaged twice about the same thing. Renaming a case silently allows a duplicate.

isPerEvent() splits the two behaviours. A renewal reminder is one per customer per day. A "cleaning done" is per event, because a household with two cars must get one for each.

Adding a setting

  1. Add the key to SiteSettings::definitions() with a label, group, rules and default. Mark it 'boolean' => true, 'rich' => true or 'long' => true as needed — the settings screen renders the right control from that.

8.2

What the server puts in the head

The site is a SPA, so everything a crawler or a link preview reads has to be in the HTML that arrives — nothing added by Vue afterwards counts. All of it is built in resources/views/site.blade.php, from the URL path and the database, before a byte of JavaScript runs.

  • A title per page, from a match ($section) on the first path segment. Add a public route, add its arm — otherwise it inherits the site-wide title and competes with the home page.
  • A LocalBusiness block from SiteSettings and the price list.
  • An FAQPage block from the live faqs rows, with strip_tags applied — a rich result renders text, and markup in it is a malformed result.
Two traps, both already sprung

Do not build the JSON with @json on a multi-line array. Blade's parser gives up on the newline inside the brackets: "Unclosed '[' on line 113". Build the array in an @php block and echo it with {!! $asJson($data) !!}.

Strip the nulls. An empty telephone in structured data is a claim there is no phone number, which is worse than the key being absent. array_filter on the way out.

Nothing here is visible in a browser, so a change that quietly drops a block goes unnoticed until somebody views the source. tests/Feature/Site/SeoTest.php is the only thing watching it — including that seo_index off withdraws the questions as well as the pages.

8.3

The banner images are generated, not bought

The four in public/images/banners/beaded-*.jpg are rendered from docs/banners/hero.html — water beading on a lit panel, four palettes off one composition:

chrome --headless=new --window-size=2400,1000 \
       --screenshot=beaded-dusk.png "docs/banners/hero.html?p=dusk"
# then dawn, monsoon, night — and convert to JPEG at ~q84

The bead positions are seeded off the palette name, so re-rendering reproduces the same image rather than quietly issuing a different one. Each is drawn dark down the left, because that is where the headline sits.

Two things this constrains

A banner carrying a picture is a dark band in both themes. BannerSlider.vue redefines the colour tokens under .hero-dark, so everything inside picks the dark set up through the classes it already uses. A light-mode page was laying a white wash over these images until they came out grey; shipping a second set for the other theme was the alternative, and this is cheaper and reads as intentional.

The headline transition must not be mode="out-in". It was, which means the outgoing headline is removed and only then does the next one begin — the hero had no words in it at all for a third of a second every six seconds. Both slides now share one grid cell and cross-fade.

8.4

When a renewed term starts

Subscription::continuesFromEndDate(), and it is the only thing that decides this:

return $end !== null
    && $end->copy()->addMonths($this->monthsOnPlan())->isFuture();

It lives on the model because two very different things read it: RecordPayment, which writes the dates, and renewalTiming(), which is what the notice on four screens promises. Those disagreeing is how a customer gets told one thing and charged for another — and they did disagree for a while, the notice still saying "restarts it from today" after the payment had started carrying on from the end date. tests/Feature/Billing/RenewalDatesTest.php renews at six different lapses and asserts the promised dates are the written ones.

A plan is a chain of periods and the chain should not have holes in it. A term runs from the day the last one ended, not from the day somebody got round to paying — which is also what the customer received, because the round keeps going through the grace period before anything is put on hold.

The condition is deliberately phrased as "would this period still be running?" rather than as a rule about status or a grace-period count. Those are settings that move; this cannot produce a plan that is expired on the day it is bought whatever anybody sets. test_a_renewed_period_is_never_already_over holds that property across six lapse lengths.

What it used to do

period_end?->isFuture() ? period_end : today() — so any lapsed plan restarted at the payment date. A customer whose plan ran to the 10th and who paid on the 17th was charged a full month for 23 days of it, and their renewal date walked a week further into the month every year.

8.5

Taking money, and the sheet that covers it

Seven screens take payments. They all go through shared/api/checkout.ts, and that is what makes the progress sheet possible: openThenPay and completeCheckout move paymentProgress through four phases, and shared/PaymentProgress.vue — mounted once per bundle — renders the two that matter.

PhaseCovered?Why
openingYesOur server is creating the payment. Nothing should be clicked twice.
gatewayNoRazorpay draws its own dialog. Covering it would block the thing the customer was asked to use.
confirmingYesThe money is taken and we are verifying the signature. A refresh here leaves somebody charged and told nothing.
idleNoNothing in flight.

confirming also registers a beforeunload handler, so a reload during the one dangerous window asks first.

The rule for new payment screens

Call a payFor* helper, or openThenPay for a new endpoint. A screen that posts and then calls completeCheckout itself will work, and will take somebody's money behind an unmarked page.

And show the receipt when it comes back. Every helper returns result.payment; a confirmation that clears itself after a few seconds, or a panel that simply closes, reads to a customer exactly like being charged and told nothing.

8.6

Switching a whole feature off

Three of them today — cloth_service, blog, team — all named in App\Support\Settings\Features, which maps each to the setting behind it. A feature has to disappear from every door at the same moment, so adding one means all five of these:

WhereWhat to add
The settingSiteSettings::definitions(), group Service, 'boolean' => true. Then the constant and its mapping in Features.
The endpointsRoute::middleware('feature:blog') around the group. A 404, not a 403 — "switched off" and "does not exist" look the same from outside.
The masters'feature' => Features::BLOG on the definition. MasterRegistry::available() then drops it from the menu and from exists(), which is what every master route checks.
The public sitemeta: { feature: 'blog' } on the route, and the link in PublicLayout. The router guard awaits whenFeaturesKnown().
The officemeta: { feature: 'blog' } on the route and feature: 'blog' on the navigation item; auth.featureOn() reads what /me sent.
Two things worth keeping straight

An ability is not a feature. One says what this person may do, the other says what the business does at all. An administrator holds every ability there is, so a menu deciding by ability alone still offers them a blog that is switched off — and no amount of permission should bring it back.

The front end fails open, the server fails closed. An unknown feature is off in Features::on(), so a typo in a route never quietly opens something up. The two front ends assume everything is on until told otherwise, because the alternative is a menu that sheds items on first paint and puts them back under somebody's cursor. The server is the one enforcing it either way.

Why a switch can look like it did nothing

The flags arrive with the session. The office reads them from /me, which is fetched once when the application starts, so saving a setting used to leave the menu offering a screen the server had just begun refusing — and the only cure was a full reload, which nobody thinks to do after pressing Save. SiteSettingsView now reloads the session as part of saving.

Or the browser is running an old bundle. With npm run dev stopped, the page falls back to whatever is in public/build, and every front-end change since that build is simply not there. Nothing warns you: the app works, it is just the wrong version of it. If a front-end change appears to have had no effect at all, check whether the served page references :5173 or /build/assets before looking anywhere else.

8.7

The receipt, and the link that needs no account

Every captured payment sends MessagePurpose::PaymentReceipt from RecordPayment::sendReceipt(), carrying a signed link to /receipt/{payment} — a printable Blade page, not the SPA.

Public on purpose. Most customers never make an account, which is the same reason the public renewal page exists, so a receipt reachable only behind a session is one that turns into a phone call. The signature is the protection: generated with the application key, refused if a character changes. It never expires, because the message it arrives in does not either.

Two traps, both sprung already

Do not use route model binding here. It resolves through the sector scope, and nobody is signed in — so the scope covers nothing and every receipt link answered 404, valid ones included. The id is taken as a string and resolved inside SectorContext::withoutScope(). This is the third time that scope has caught an unauthenticated page.

Blade only sees a directive at a token boundary. Received@if (…) compiles as literal text and leaves the @endif with nothing to close, which is a 500 on the finished page and not a build error. Put a space or a newline before it.

The wording uses {paid_amount}, not {amount}. The second is what the plan costs today; a receipt has to say what was taken, on the day it was taken, under the invoice number it was taken under — and MessageTemplate::valuesFor() deliberately leaves the receipt placeholders blank rather than defaulting them from the plan, so a template that asks for them without a payment renders empty instead of wrong.

8.8

What goes stale when you save something

resources/js/shared/api/refresh.ts

Reference lists are cached hard — five minutes for the cleaners, the price list and the geography, because they are read on nearly every screen and change a few times a month. The cost is a cache that is right about everybody else's edits and wrong about your own.

Every screen used to clear only its own keys, which is exactly the half that was never the problem: the list in front of you refetched, and the four other screens reading the same records did not. Add a cleaner on People, walk to Subscriptions, and the picker did not offer them for another five minutes — which from the office's side means the cleaner was not saved, so they save them again.

// Not this
await queryClient.invalidateQueries({ queryKey: ['users'] })

// This — the fan-out is named once, in one file
await refreshAfter(queryClient, 'people')

Prefix matching does the rest: clearing ['cleaners'] also clears ['cleaners', <plan id>], so the per-plan pickers need no naming. The kinds are people, masters, customers, subscriptions, payments, roles and cloth; several can be passed at once, as the plan form does with 'subscriptions', 'customers'.

A key that does not exist fails silently

invalidateQueries on a key nothing uses is not an error — it does nothing, quietly, and the screen it was supposed to refresh stays stale. The first draft of this file named ['payment']; the detail panel actually uses ['payment-detail'], so the open receipt would have gone on showing the old figures.

Worth checking a new entry against the real keys rather than trusting it:

grep -rhoE "queryKey: (computed\(\(\) => )?\['[a-z-]+'" resources/js \
  | grep -oE "\['[a-z-]+'" | tr -d "['" | sort -u

The front end

9.1

Two bundles

vite.config.ts — builds site/main.ts and admin/main.ts separately

A visitor reading the price list does not download the reports screen or the masters form. The portal lives inside the admin bundle because it needs the session and the auth store; it has its own layout and its own routes, and the router keeps the two apart by role, not by ability:

if (auth.isCustomer !== (to.meta.customer === true)) return home;

Three URL spaces, one blade decision

routes/web.php
Route::view('/login',        'app')->name('login.page');
Route::view('/app/{any?}',   'app')->where('any', '.*')->name('app');
Route::view('/my/{any?}',    'app')->where('any', '.*')->name('portal');

Route::view('/{any?}', 'site')

    ->name('site');
The trap

Any URL not in that exclusion list falls through to the public bundle, whose catch-all route redirects to the home page. When /my was missing here, every reload of a customer's page bounced them to the public home page and it looked like a session bug. If you add a URL space, add it to both the Route::view list and the negative lookahead.

9.2

Where logic goes

Not in .vue files. Anything with a decision in it — the signup flow, row selection, the subscriptions API — is a .ts module beside the views that use it (site/signup.ts, admin/shared/useRowSelection.ts, admin/shared/subscriptions.api.ts, portal/portal.api.ts, shared/api/checkout.ts). A component binds and renders; it does not decide.

This is applied to new work and to components as they are touched, not retrospectively across all of them. A bulk extraction was attempted and reverted; it broke 190 type checks in one go. Do it one component at a time, with the type check green between each.

Data fetching

TanStack Query throughout, with the query key naming the thing and its filters. Mutations invalidate rather than patching caches by hand. Axios lives in shared/api/client.ts and carries the Sanctum cookie.

Theme

One set of CSS custom properties in resources/css/app.css, light and dark, shared by both bundles. Use the token classes (bg-surface, text-ink, border-line, text-accent) rather than raw Tailwind colours, or the component will be wrong in one of the two themes.

Type checking

npx vue-tsc --noEmit

Run this rather than npm run build while working — npm run dev is normally already running and a build fights it.

The ordering is a design decision

Backup first, so a later job going wrong leaves a copy from before it did. Settlement before reminders, so nobody is chased for money they already paid. Holds last, so they act on a corrected picture. Pruning after the backup, so a retention rule can never be the reason something is unrecoverable.

Every job is withoutOverlapping, onOneServer and runInBackground. Keep all three on anything you add: an unattended job that runs twice is worse than one that does not run at all.

Section 13

Bugs this codebase has already had

13.1

Each of these cost real time to find. They are recorded because every one of them is easy to reintroduce.

The timezone

v1 ran on Asia/Kolkata; v2 started on UTC. Every imported timestamp was mislabelled by five and a half hours, so date filters found nothing and nobody could see why. APP_TIMEZONE=Asia/Kolkata is not a preference.

Sign-in codes that never expired

login_codes.expires_at was a MySQL TIMESTAMP, which carries an implicit ON UPDATE CURRENT_TIMESTAMP. Every wrong guess touched the row and pushed the expiry forward, so a code lived forever. Migration 0001_01_01_000022 changes it to DATETIME and spends the outstanding ones. Never use TIMESTAMP for an expiry.

Two hundred customers in the wrong books

A sector was pointed at another franchise and nothing anybody could see changed. Every record carried its own branch_id — a copy of where the customer lived — and that copy was what the scope read, so the picker appeared to work while two hundred customers stayed put and the new owner signed in to a screen of zeroes.

A cache of a derived fact will drift, and nothing was comparing the two. The fix was to stop storing it: territory is now worked out from customers.sector_id against user_sector on every query. See section 03.

PowerShell will corrupt your files

Two ways, both silent. Set-Content -Encoding utf8 on 5.1 writes a BOM, and PHP will not parse a file that starts with one — 62 files at once. And a -replace round-trip through ReadAllText/WriteAllText mangled every non-ASCII character in eight more, turning … into mojibake that a second "repair" pass made worse.

Use sed, which is byte-oriented, or the editor. If a file is already mangled, restore it from git rather than trying to decode it back.

Every master list at once

A variable that the listing closure never captured — use ($definition, $filters) where the body also wanted $request. One line, and it took out all twenty masters simultaneously: the price list, the geography, the banners, the templates. The screen said "Something went wrong" and the reason was only in the log.

PHP closures capture explicitly, so this class of mistake is silent until the line runs. It shipped because the Masters screen had no test at all — the single most load-bearing screen in the system, and nothing opened it. MasterListingTest now walks the registry.

₹225 on the page, ₹1,872 at the gateway

The public renewal page loaded the vehicle and the customer inside the sector scope. Nobody is signed in on that page, so the scope covers nothing and both relations came back null — and nothing threw. The price book, asked to price a plan with no car and no address, dropped the vehicle category and the society surcharge and answered with what was left.

A customer saw ₹225, pressed Pay, and Razorpay asked them for ₹1,872. The card above it showed an empty registration beside an empty name, which is the same bug and was the visible half nobody connected to the price.

The general rule

Anything reached without a session must resolve its records inside SectorContext::withoutScope() — and that includes relations loaded for something else, like the two the price book reads. Fail-closed scoping is correct and did its job; the mistake was reading through it and then treating a null relation as a plan with no car.

A second defect sat behind it: the payment was opened from the plan's stored amount_paise, which is what it cost the last time it was bought, so quote and charge could disagree even once the quote was right. Renewals now price and write before StartPayment is asked. tests/Feature/Billing/PublicRenewalTest.php pins both.

An editor that would not open at all

A computed declared above the query it reads. societyId referenced existing forty lines before existing was declared — which JavaScript allows right up until something evaluates it, and useQuery unrefs its queryKey during setup to build the first observer. ReferenceError: Cannot access 'existing' before initialization, thrown while mounting, so the dialog never appeared and the Edit button read as dead.

The lesson is narrower than "declare things in order": a reference inside an arrow function is deferred, but TanStack evaluates query keys eagerly, so a key that reaches a later const is a runtime error rather than a lint warning. vue-tsc passes either way.

A form that opened blank the second time

The plan editor filled itself with watch(existing, …) and no immediate. The dialog is behind a v-if, so it unmounts on close — and TanStack Query hands cached data over during the first render of the remounted component. The watcher is registered after that, nothing changes, and it never fires.

So: open a plan, close it, open the same plan again, and every dropdown reads Choose…, the car number is a dash, and the price panel says it needs a duration. Saving from there is the obvious next thing somebody does. It was reported as "cancel the payment window, then press Edit" because that sequence opens the dialog twice; it has nothing to do with payments.

Where this can bite again

Any component that is unmounted and remounted and fills a form from a query keyed on an id. Panels that stay mounted are fine — the key changes and the data genuinely transitions. Adding { immediate: true } costs one no-op call and removes the class, so put it on every one of them.

₹699 on the edit screen, ₹779 at the gateway

The plan editor's price panel quoted without society_id, so it priced the plan as though the customer lived nowhere in particular and dropped an ₹80 surcharge. Nothing on that screen mentions the society, so the office had two figures and no way to tell which was wrong.

This is the third time the same omission has shipped — the public renewal page and the customer's renew panel both had it. Any quote for an existing customer needs the society. PriceBook::forRenewal() reads it from the customer and is the safe path; a hand-built call to /pricing/quote is where it goes missing.

The missing use statement

A complaint was created and then the notification's own catch block threw, because Log was not imported. The customer saw a 500 and the complaint existed. ClassNamesResolveTest now walks app/ and fails on any name that will not resolve.

Every portal reload going home

/my/* was not listed in routes/web.php, so it fell through to the public bundle whose catch-all redirects home. Covered in section 09; it was reported twice as a session bug before the cause was found.

A cleared setting reverting to its default

SiteSettings::read() used ??, which cannot tell a stored null from a missing row. Emptying a policy page and saving brought the shipped wording straight back, and looked like the save had failed. It uses array_key_exists now.

A settings cache that hid new settings

The SEO fields were added and the site kept serving the fallback title until somebody ran cache:clear by hand. The cache now rebuilds itself when the number of definitions changes.

Imported payments with no invoice number

All 492 of them. eswachh:backfill-invoice-numbers exists for this and the importer calls it.

A dropdown clipped by its own container

The plan list's action menu was cut off by an overflow-x-auto ancestor. It is teleported to <body> with fixed positioning and repositioned on scroll and resize. If you add a menu inside a scrolling table, do the same.

Section 14

Cutting over from v1

14.1

v1 is still live and still taking orders, and features have been added to it since v2 was started. Two different questions follow from that, and only one of them is real work.

The code does not need porting

v1's newest migrations are complaints, cleaner attendance, sector_user, the franchise-owner role, and payment tracking on payment_history. Every one of those already exists in v2, built natively rather than carried over — sector scoping is the whole tenancy model here, complaints and attendance have their own screens, and payments have carried gateway ids since the first day.

So there is no v1 code to migrate. What is left is a data question: does the content of those newer tables come across? Today it does not — see 14.3.

Catching up the data is one command, run again

The importer is idempotent, and this was checked rather than assumed. Importing the same database twice:

after 1st import: customers=212 subs=222 payments=492 map=1519
after 2nd import: customers=212 subs=222 payments=492 map=1519

And importing an older snapshot, then a newer one on top of it — which is exactly what a second run against a still-live v1 looks like:

older snapshot:      customers=203 subs=213 payments=481
newer on top:        customers=212 subs=222 payments=492
duplicate invoices:  0

The delta arrives and nothing doubles. legacy_references is what makes that true: every record the importer creates is written there against its v1 id, so a second run finds the mapping and updates rather than inserts.

14.2

The sequence on the day

  1. Take a fresh dump of the production v1. Not one of the local snapshots — they are months apart from each other, let alone from production, and picking the wrong one silently imports an old world.
  2. Load it locally and point LEGACY_DB_DATABASE at it. The command refuses anything without an orders table, so a v2 database by mistake stops here rather than half way through.
  3. php artisan eswachh:import --dry-run and read the skipped table. Every payment reporting "no matching subscription" is normal in a dry run — nothing was written, so nothing is in the map yet.
  4. php artisan eswachh:import. Existing records update; new ones are added.
  5. Check the counts against v1's own: orders against subscriptions, payment_history against payments.
  6. Stop v1 taking orders before the final run, or the last few minutes of trading are stranded in a system nobody is watching any more.
Rehearse it, then rehearse it again

Because it is idempotent, the run on cutover day should be the fiftieth time you have done it, not the first. Import a fresh dump weekly in the run-up: it costs a command, and it turns the day itself into something boring.
